# Registered personalized-state repeat controller

The new `build/launch-host-state-repeat.py` and
`build/verify-host-state-repeat.py` entry points bind a fresh state construction
to the [second production root build](../../production-host-roots-repeat.md). The
[controller review](../../evidence/state-repeat-controller-20261107.json) approves
source integration. The [actual state repeat](../../production-host-state-repeat.md)
now also passes frozen construction, full readback and independent artifact review.
The historical state controllers and their original evidence remain unchanged.

The actual committed-source `--plan` for revision `3221a1c` passes on the builder.
Privileged Ubuntu validation passes **1,621 unit tests without skips**, five shell
suites, five SD assembly cases, Bash syntax and TOML parsing. These checks
establish no hardware acceptance.

Each adapter authenticates its entire historical controller template by SHA-256,
holds its physical ancestors and single regular-file descriptor, and checks its
identity and bytes through final publication. Only an explicit set of constant
AST values changes: the registered producer revision/evidence, root phase/output
and executing controller source key. Counts and complete AST tests reject drift;
no caller-supplied source, registration or substitution is accepted. All original
isolation, capsule authentication, capacity, identity, filesystem and cleanup
checks remain active. Additional checks bind the exact raw, canonical JSON and
Git blob pins of the new root evidence and report the original template pin.

The adapters use the same CLI arguments as the historical state launcher and
reader. The fixed parent root receipt is:

```text
/var/lib/a733-clean-replay-20261106/host-roots-timesync-repeat-01/receipt.json
SHA256 64e413bbdd158da4e998a193e32d40c8a62c65d3051c6cb2f6aa4b955ab2efbc
```

Use a fresh state build tag and an explicit new UUID. Both adapters reject the
installed `00fd936c-49fb-4fea-87c8-928b9c1599e0`, the first candidate's
`fc8bbef6-9385-4ddb-90ba-e41eaccc035b`, zero and root-slot UUIDs. Machine-id
remains newly generated by the existing state recipe; SSH host-key storage must
remain empty until first boot. Per-installation state is compared semantically,
not expected to have identical bytes or identity.

Before executing, commit the reviewed source, run its actual CLI with `--plan`
from the committed checkout, verify builder resources and parent artifacts, then
construct only regular-file state in a new frozen namespace phase. Follow with
full read-only verification against that exact new receipt. Retain failures and
never overlay a used tag. Downstream bootstrap and full NVMe controllers still
bind the first state construction; they need their own explicit reviewed repeat
bindings after new state evidence exists.

These adapters neither flash storage nor repair the currently installed host.
Use the [existing-install repair](../../installed-host-repair-20261107.md) on the board;
keep published operator images and delivery endpoints unchanged. Actual SSH,
KVM guest execution, recovery, SPI boot, endurance, zero routine SD writes and
independently reproduced deployment remain release gates.
